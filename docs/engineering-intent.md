# 校园活动管理系统 V1.0 工程意图

## 1. 业务问题与用户目标

校园活动信息通常分散在群聊和临时通知中，学生难以集中了解活动、确认剩余名额和管理自己的报名；活动组织教师也缺少统一的发布、维护和查看报名名单的入口。

- 学生希望快速找到仍可报名的活动，完成报名或取消报名，并查看自己的报名记录。
- 活动组织教师希望创建、修改、发布或取消活动，并掌握报名人数与名单。

## 2. V1.0 需求

| 编号 | 用户 | 需求描述 | 优先级 | 验收依据 |
| --- | --- | --- | --- | --- |
| REQ-01 | 学生、教师 | 用户能够登录和退出；学生能够注册，教师使用预置账号 | 高 | 新学生注册后可登录；教师账号可进入教师工作台；错误凭据有提示 |
| REQ-02 | 学生 | 浏览已发布活动并查看时间、地点、容量和活动说明 | 高 | 学生只能看到已发布活动，且能打开详情 |
| REQ-03 | 学生 | 报名符合条件的活动 | 高 | 系统阻止重复、已满、已取消或已开始活动的报名 |
| REQ-04 | 学生 | 查看并取消自己的有效报名 | 高 | 取消后报名状态更新且活动名额恢复 |
| REQ-05 | 教师 | 创建、编辑、发布和取消自己负责的活动 | 高 | 草稿不对学生展示；状态变化立即反映到学生端 |
| REQ-06 | 教师 | 查看所负责活动的报名人数与学生名单 | 中 | 名单与有效报名记录保持一致 |

## 3. 需求取舍

1. V1.0 使用浏览器本地持久化，不建设真实服务器数据库，以便在有限时间内验证完整业务闭环。
2. 学生可以自行注册，教师账号只由系统预置，避免普通用户自行获得管理权限。
3. 暂不实现报名审核、消息通知、文件上传、统计报表和多级管理员，避免扩大版本范围。

## 4. 工程意图

- 建设目的：为校园活动提供统一、可操作的发布和参与入口。
- 本轮范围：完成登录、学生注册、活动浏览与报名、教师活动管理和报名名单查看。
- 重要约束：角色权限必须隔离；草稿不可报名；容量不能超限；同一学生不能重复有效报名；活动开始后不可报名或取消。
- 完成依据：六项需求均有可复现的验证场景，学生与教师核心流程均能在浏览器中完整执行，刷新页面后数据仍保留。
- 需求关系：本工程意图对应 REQ-01 至 REQ-06。

## 5. 总体设计

系统采用单页工作台结构：界面层负责登录、列表、详情和表单；领域规则层负责权限、状态、容量和重复报名判断；存储层负责带版本号的浏览器本地数据。页面不直接修改存储数据，所有业务操作先经过领域规则校验。

## 6. 核心业务流程

### 学生报名

登录 → 浏览已发布活动 → 查看详情 → 校验活动状态、时间、容量和重复报名 → 创建有效报名 → 更新剩余名额。

### 教师发布活动

登录 → 创建活动草稿 → 校验必填信息和时间范围 → 发布活动 → 学生端可见 → 查看报名名单；必要时可编辑或取消活动。

## 7. 数据对象

| 数据对象 | 关键字段 | 用途 | 关系 |
| --- | --- | --- | --- |
| User | id、name、email、passwordHash、salt、role | 保存原型用户身份 | 学生关联报名；教师关联活动 |
| Activity | id、title、description、location、startAt、endAt、capacity、status、organizerId | 保存活动及状态 | 属于一名教师，拥有多条报名 |
| Registration | id、activityId、studentId、status、registeredAt、cancelledAt | 保存报名及取消记录 | 连接学生与活动 |
| Session | currentUserId | 保存当前登录状态 | 指向当前用户 |

## 8. 关键设计决策

1. 认证仅用于课堂原型：密码使用 Web Crypto 生成加盐摘要，不保存明文；不宣称具备生产级安全性。
2. 活动状态采用 `draft`、`published`、`cancelled`；是否已开始根据当前时间动态判断。
3. 取消报名保留记录并改为 `cancelled`，便于说明业务变化与验证名额恢复。
4. 所有本地数据使用带版本号的统一存储结构，首次访问时写入演示教师和活动数据。
